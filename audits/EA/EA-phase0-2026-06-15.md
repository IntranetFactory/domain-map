# EA Phase 0 — Vendor Surface (Enterprise Architecture)

Scope note: EA is an **umbrella** discipline. The catalog already masters the application layer (APM, domain 10) and the process layer (BPA, domain 136), and tracks `business_capability_maps` (APM) / a nearby `BUSINESS-CAPABILITY-MAP` concept. This Phase 0 finds EA's **distinctive** master set: the cross-layer artifacts (repository/metamodel, ArchiMate model store, technology standards & reference models, roadmaps/transformation, principles, decisions) that no neighbor owns. Every entity below carries an **Ownership** verdict.

## Governance surfaces (EA-mastered, non-statutory)
**EA is NOT a statutorily-regulated market.** TOGAF and ArchiMate are **standards frameworks / configuration-catalog artifacts**, not statutory compliance regimes — there is no FCRA/HIPAA/SOX analog, and no per-jurisdiction filing/obligation surface should be invented. The governance that EA *does* master is **internal architecture governance**:
- `architecture_review_boards`, `architecture_review_decisions` — ARB workflow and verdict log.
- `compliance_assessments`, `standard_exceptions` — conformance of an application/component to an `architecture_standard`, plus the waiver/exception register. This is *standards conformance*, not regulatory compliance.
- `architecture_decision_records` — ADR log (decision, context, status, supersedes).
- `architecture_principles` — governance guardrails (LeanIX, Ardoq, BiZZdesign all model these).

TOGAF ADM phases, the ArchiMate element/relationship catalog, and viewpoints are all **Configuration-templates** (`metamodel_element_types`, `metamodel_relationship_types`, `architecture_viewpoints`), not compliance entities.

## Modularization hypothesis
Built **only from EA-MASTER** entities. Rule #14: every module has >=1 master; EA's >=3 capabilities (repository, technology governance, transformation) warrant >=2 full modules.

**Module 1 — EA Repository & Metamodel** (the architecture backbone)
Scopes: the typed model store and its schema. Holds `architecture_repositories`, `metamodel_element_types`, `metamodel_relationship_types`, `architecture_model_artifacts`, `element_relationships`, `element_lifecycle_states`, `architecture_viewpoints`, `architecture_diagrams`, `architecture_principles`, `architecture_decision_records`.

**Module 2 — Technology Standards & Reference Architecture** (the "what's allowed / what's recommended" layer)
Scopes: standards governance and technology direction, distinct from APM's *inventory*. Holds `architecture_standards`, `standard_exceptions`, `reference_architecture_models`, `technology_radar_entries`, `technology_lifecycle_phases`, `compliance_assessments`, `architecture_review_boards`, `architecture_review_decisions`.

**Module 3 — Architecture Roadmap & Transformation** (as-is to to-be)
Scopes: state planning and migration. Holds `architecture_roadmaps`, `baseline_architectures`, `target_state_architectures`, `transition_architectures`, `architecture_gaps`, `architecture_work_packages`, `transformation_initiatives`.

**Module 4 (conditional) — Business Architecture / Capability** — only if `BUSINESS-CAPABILITY-MAP` is folded into EA rather than left standalone. Would hold `business_capabilities`, `capability_assessments`, `value_streams`. Left OUT of the minimal EA set for now (see verdict).

## Boundary verdict
**(a) Distinct domain?** Yes. EA is *not* APM+BPA+capability-map re-bundled. APM masters the application *inventory* (cost/value/fit), BPA masters *process models*, capability-mapping masters *capabilities*. None of them owns the **metamodel/repository, the ArchiMate model artifacts, technology standards & reference architectures, the technology radar, architecture principles, ADRs, ARB governance, or the baseline-to-target roadmap with gaps/transition architectures.** All five vendors converge on exactly this cross-layer governance-and-direction surface, which is EA's reason to exist. EA should be bounded to **consume** `enterprise_applications`/`technology_platforms` from APM and `business_processes` from BPA, not re-master them.

**(b) Minimal EA-MASTER set (the justification):** `architecture_repositories`, `metamodel_element_types`, `metamodel_relationship_types`, `architecture_model_artifacts`, `element_relationships`, `element_lifecycle_states`, `architecture_viewpoints`, `architecture_diagrams`, `architecture_principles`, `architecture_decision_records`, `architecture_standards`, `standard_exceptions`, `reference_architecture_models`, `technology_radar_entries`, `technology_lifecycle_phases`, `compliance_assessments`, `architecture_review_boards`, `architecture_review_decisions`, `architecture_roadmaps`, `baseline_architectures`, `target_state_architectures`, `transition_architectures`, `architecture_gaps`, `architecture_work_packages`, `transformation_initiatives`. (Capability entities are CAP-MAP, not part of the minimal set.)

**(c) EA-vs-APM technology-layer collision (APM q8):** Real overlap, resolvable by a clean **inventory vs. governance** split. APM's q8 (split `technology_platforms` into products/services/platforms; add tech-risk: `vulnerabilities`, `application_risks`, `lifecycles`, `standards`, `controls`, `obligations`) should keep the **operational inventory and risk** half: products/services/platforms instances, `vulnerabilities`, `application_risks`, `controls`, `obligations`, and the per-instance lifecycle *state* a deployed component is in. **EA should own the prescriptive/normative half:**
- `architecture_standards` (the catalog of *approved/recommended* standards) — **EA**, not APM's per-app `standards`. APM should *reference* EA's standard; EA owns the standard definition and its `compliance_assessments`/`standard_exceptions`.
- `technology_lifecycle_phases` (the *phase model* / radar policy: emerging/adopt/contain/retire) — **EA** owns the policy catalog; APM's `lifecycles` records a specific component's current phase against it.
- `reference_architecture_models` — **EA**, unambiguously; APM has no such concept.

Net: if both ship, define `technology_standards`/`technology_lifecycle_phases`/`reference_architecture_models` **once in EA** and have APM consume them via reference, avoiding a duplicate master. If APM q8 lands first with a local `standards` table, flag it for promotion into EA at EA's Phase B.
