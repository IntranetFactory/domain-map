## Boundary calls (what DCG masters vs consumes)

The central Rule #22 calls for DCG, each grounded in vendor reality:

- **Data access governance: DCG masters policy authoring; access ENFORCEMENT is a separate market.** Every flagship catalog masters `data_access_policies` as authored governance rules (Collibra policy, Purview access policy at domain/product/term level, Informatica AXON policy). BUT the runtime enforcement/provisioning is increasingly a SEPARATE product: Atlan's marketplace "provisions access automatically via Immuta in Snowflake or Databricks", i.e. Atlan authors the request and delegates enforcement to Immuta. Immuta positions itself as a data-access-governance / provisioning company distinct from the catalog. Databricks is the counterexample where enforcement is native (Unity Catalog ABAC). Conclusion: DCG masters `data_access_policies` (the rule) and `data_access_requests` (the workflow instance), and HANDS OFF enforcement to DSPM/DLP (this is exactly handoffs 158/260/261/264/709). It does NOT master runtime enforcement. The current footprint is correct; access governance is a DCG module, not a separate domain.

- **Classification: a real workflow surface but not a standalone module here.** Collibra and Purview both treat classification as a distinct workflow (automated scan to proposed to approved to enforced). This grounded the original q-file's "7-module split elevates Classification" option (d). But the vendor packaging does NOT consistently separate classification from access governance: Purview applies classifications then drives access policies off the same glossary-term linkage; Databricks fuses classification (governed tags) with ABAC. So classification + access policy belong in ONE Access Governance module. The 7-module split is over-fine relative to how vendors package it. (Reversal candidate: see q1 below.)

- **Lineage: a first-class surface in every vendor, but presented as a tab/explorer.** All 6 vendors master lineage. The packaging question (does it warrant its own module?): data.world (Eureka Explorer), Atlan (lineage in the asset view), Databricks (lineage beneath every interaction) present lineage as an INTEGRATED view on the asset, not a separate workflow product. Collibra and Open Metadata run distinct lineage modules with their own ingestion. The split is editorial; lineage has enough first-class entities (edges + impact analyses + query lineage) to be its own module, and the prior 6-module recommendation keeps it separate. No reversal, but the q-file flags the fold-into-catalog option honestly.

- **Metric definitions: DCG carries a catalog-side copy; the headless layer masters it.** Unity Catalog surfaces "certified metrics" and Atlan/data.world surface metrics, but the standalone metrics layer (dbt Semantic Layer / Cube) is a SEPARATE category that masters the metric definition. Our catalog already has METRICS-LAYER (137). DCG's `metric_definitions` (252) is currently mastered by DCG; the vendor evidence says the metric is mastered in the semantic layer and the catalog carries the certified/governed copy. This is a multi-master / ownership-coordination point with METRICS-LAYER, surfaced as a boundary note (not a forced reversal: dbt itself notes catalog owners govern metric definitions, so a co-master shape is defensible).

- **Data products / data contracts: DCG masters data products; data contracts are an emerging adjacent market.** All 6 vendors master `data_products`. Data contracts are native only in Atlan (machine-readable contracts enforcing schema/quality/SLA) and emerging in Collibra (2024.11); Gable.ai / Datacontract.com / Confluent Schema Registry / Buf are a distinct pure-play market. So data contracts are a B3 candidate domain, not a confirmed DCG master. Data marketplace listings are a common surface (Collibra Marketplace, Atlan Marketplace, Informatica Data Marketplace) and belong in the Data Products module, not (yet) a separate DATA-MARKETPLACE domain.

## Workflow substrate (lifecycle and transitions)

- **Asset lifecycle (discovered to curated to certified to deprecated)** is universal: every vendor moves a crawled asset from discovered, through curation/stewardship, to certified (Collibra/Atlan/Informatica) or certified-tag (Databricks Beta 2025), to deprecated/archived.
- **Glossary term lifecycle (draft to approved to published to deprecated)** is explicit in Collibra/Atlan/Informatica/Purview (term approval workflows). Databricks is the weak case (governed tags, no approval cycle). Grounds q5: glossary_terms IS workflow-bearing.
- **Classification lifecycle (proposed to approved to enforced)** is a real workflow in Collibra/Purview (auto-classify proposes, steward approves, policy enforces); the approved classification rule should freeze (submit-lock). Grounds q10.
- **Access policy lifecycle (drafted to approved to enforced)** with a single named approver is the textbook submit-lock + single-approver shape (policy author drafts, governor signs off, then locked). Grounds q7.
- **Certification (granted by one accountable owner)** is single-approver by construction across all vendors (a data owner/steward certifies). Grounds q9.
- **Stewardship assignment carries an identifiable employee** (the steward is a named person) in all vendors, which is personal data. Grounds q8.
- **Data domains are author-once reference scopes** ("Finance", "HR") that rarely change. Grounds q4 (config-shape exemption).
- **Usage metrics are emitted telemetry**, not a record someone moves through states. Grounds q6 (config-shape / signal exemption).

## Marketed product surfaces (grounds the module-split call)

How vendors package the domain into buyable surfaces:

- **Collibra** packages by PRODUCT: Data Catalog, Data Governance, Data Lineage, Data Quality, Data Marketplace, Data Privacy, AI Governance are named separate products on one platform. This is the strongest evidence for a multi-module split, and it keeps lineage and marketplace as distinct surfaces.
- **Atlan** packages by EXPERIENCE on one active-metadata core: Discovery/Catalog, Lineage (on the asset), Governance (glossary + classification + contracts), Data Products + Marketplace. Lineage is a view, not a separate product; data products + marketplace are one surface. Favors fewer, broader modules.
- **Microsoft Purview** packages by CAPABILITY tier inside Unified Catalog: Data Map (scan/classify), Unified Catalog (curate/glossary/data products), access policies, plus the broader compliance suite. Catalog + classification + access are one continuum.
- **Informatica CDGC** packages by IDMC service: CDGC (governance + catalog + glossary + stewardship) + Metadata Command Center (harvesting) + Data Marketplace as integrated-but-named services.
- **Databricks Unity Catalog** packages as ONE governance layer beneath the lakehouse (no sub-product split); favors a tighter shape, but it is the lakehouse-native outlier.

## Modularization hypothesis

The vendor evidence supports a 5-to-6 module shape. The 6-module shape (Catalog / Lineage / Glossary / Stewardship / Access Governance / Data Products) matches Collibra's named-product packaging and keeps each surface small. The strongest vendor-grounded simplification is folding Classification INTO Access Governance (Purview/Databricks fuse them; only Collibra treats classification as semi-distinct), which argues AGAINST the 7-module "elevate Classification" option. Atlan's evidence supports a tighter 5-module shape that folds Lineage into Catalog (lineage-as-asset-view), but Collibra/Open Metadata keep lineage separate, so the 6-module shape with Lineage standalone remains the lead recommendation.

- **6-module (Collibra named-product shape, lead):** Catalog (data_assets + data_domains + metadata_collection_jobs + collaboration), Lineage (lineage edges + impact analyses + query-lineage consumer), Glossary (glossary_terms + ontologies), Stewardship (stewardship assignments + certifications), Access Governance (classifications + sensitivity labels + access policies + access requests), Data Products (data products + marketplace listings + metric-definition copy + usage metrics).
- **5-module (Atlan active-metadata shape):** as above but Lineage folds into Catalog.
- **3-module (Databricks lakehouse-tight shape):** Core (catalog + lineage + glossary), Governance (stewardship + access governance), Data Products. Defensible if DCG ships alongside a lakehouse stack.
- **7-module is NOT vendor-supported:** elevating Classification to its own module over-fines a surface that Purview/Databricks/Atlan all fuse with access governance. This is the reversal candidate against the prior q-file recommendation (d).

All shapes clear the Rule #14 floor (DCG has well above 3 capabilities). The lead remains 6 modules; the choice between 5 and 6 is editorial (lineage as tab vs product). The 7-module option should be flagged as the weakest, not co-equal.
