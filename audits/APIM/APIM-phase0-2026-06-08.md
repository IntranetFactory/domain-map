# APIM Phase 0 - Vendor Surface (2026-06-08)

Rule #22 remediation pass for API Management (domain_id=79). The prior q-file leaned on
generic "matches how the major API platforms present their product" reasoning with no named
evidence. This report grounds every market-shape recommendation in the flagship vendor surface
studied this pass (2025-2026 product docs). Research only: no DB writes.

Diversity check met: pure-play gateway specialist (Kong), design-first specialist (Postman),
cloud-native runtime (AWS), three full-lifecycle suites (Apigee, Azure, IBM, MuleSoft). APIM is
not a regulation-mandated market the way US ATS is for FCRA, so there is no single compliance
specialist anchor; GDPR (developer PII) and SOX (gateway audit logs, change control) are the
load-bearing regimes and apply across vendors rather than via a specialist.

## Per-decision verdicts (these drive the q-file)

**Module split (B2-S1, the gate).** Vendor packaging is the evidence. Apigee, Azure APIM, Kong
Konnect, and IBM API Connect all separate a **design/lifecycle** surface (specs, versions,
Exchange/draft products) from a **gateway/runtime** surface (gateways, deployments, policies,
rate/quota config, backends), from a **consumer/access** surface (products, subscriptions/
contracts, apps, keys, usage), from a **developer portal** surface (the published catalog +
docs). AWS and Kong OSS collapse to a thinner control/data-plane split. So the 4-module shape
(a) mirrors flagship full-platform packaging; the 2-module control/data-plane shape (c) mirrors
gateway-only vendors. Recommend **(a) 4 modules** because APIM's loaded surface already spans
all four areas and the developer-portal surface is a distinct buyer (the developer-experience
team) that vendors market separately (Apigee, Kong, Azure, IBM, Postman all ship a named Dev
Portal product surface).

**Pattern flags (B2-S2).** The evidence confirms all four proposed flips:
- `api_specifications.has_submit_lock=true`: published specs freeze. AWS API Gateway deployments
  are immutable snapshots of a stage; IBM API Connect staged Products become a "specific version"
  not editable in place; the broad market practice gates breaking changes behind a NEW
  revision/version rather than editing a published one. Contract testing pins to an immutable
  revision (the published-spec-is-the-contract pattern). CONFIRMED.
- `api_specifications.has_single_approver=true`: one API product owner approves the breaking-
  change checklist. The market's breaking-change discipline (gate behind new revision, single
  changelog, owner sign-off) supports a single accountable approver. CONFIRMED.
- `api_policies.has_single_approver=true`: one platform-engineering reviewer per policy. Policies
  govern live access (Azure/Kong/Apigee policy/plugin model); a single accountable approver per
  policy is consistent with how the runtime surface is operated. CONFIRMED (lighter evidence than
  the spec flags; this is operational discipline, not a vendor-modeled field).
- `api_consumers.has_personal_content=true`: developer/consumer contact details are PII. Every
  vendor's developer portal registers a Developer (Apigee), Consumer Organization (IBM), client
  app owner (MuleSoft) with contact details. GDPR applies. CONFIRMED.

**Regulations (B2-S3).** GDPR is clearly load-bearing (developer PII on every portal). SOX
applies to gateway audit logs + change control for public companies. PCI-DSS applies only if an
API touches card data (conditional). Recommend GDPR + SOX as the defensible baseline; PCI-DSS as
the conditional third. The prior recommendation of GDPR + SOX + PCI-DSS (a) is reasonable but
PCI-DSS is genuinely conditional, so the honest framing is GDPR + SOX always, PCI-DSS if payment
APIs.

**Substrate entities (B3-S1).** The surface matrix IS the answer: load `api_products`,
`api_subscriptions`, `api_plans`/rate plans, `oauth_clients`/developer apps, `api_keys`,
`developer_portals`, `api_documentation`, separable `api_rate_limits` + `api_quotas`, and
`backends`/upstream services. `api_change_proposals` is Specialist (Postman API network only);
`api_audit_logs` may route to API-SEC if that domain promotes. Additive, non-blocking.

## Modularization hypothesis

Four full modules, mirroring flagship full-platform packaging:

1. **APIM-DESIGN-LIFECYCLE** (`api_specifications`, `api_versions`): design-first authoring,
   versioning, breaking-change governance; the Apigee/Postman/Exchange design surface).
2. **APIM-GATEWAY-RUNTIME** (`api_gateways`, `api_deployments`, `api_policies`): plus the
   separable `api_rate_limits` / `api_quotas` config and `backends` (the data-plane + policy
   surface; Kong/AWS/Azure runtime).
3. **APIM-CONSUMER-MGMT** (`api_consumers`, `api_usage_metrics`): plus `api_products`,
   `api_subscriptions`, `api_plans`, `oauth_clients`, `api_keys` (the access + monetization
   surface; Apigee/IBM/MuleSoft consumption model).
4. **APIM-DEVELOPER-PORTAL** (`developer_portals`, `api_documentation`, `api_categories`): the
   published self-service surface; a distinct buyer/team across Apigee, Kong, Azure, IBM, Postman).

The 4-module shape is the recommended call because the loaded surface already spans all four
areas and each is a separately-marketed vendor product surface. The 2-module control/data-plane
shape (c) only fits gateway-only vendors; the 3-module shape (b, folding portal into design) is a
reasonable compromise if the developer-portal substrate is deferred, but the vendor evidence
treats the portal as a first-class product surface, so (a) is preferred.
