## The contested overlap: BI-native semantic layer vs standalone headless layer (METRICS-LAYER)

This is the central Rule #22 boundary call for BI. The market splits the "semantic model / governed metric" concept two different ways, and the catalog already encodes both:

- **BI-native (embedded) semantic layer.** Every flagship BI vendor ships its OWN model embedded inside the tool: Power BI's tabular/DAX semantic model, Looker's LookML model, Qlik's master items, ThoughtSpot's Model (ex-Worksheet). The metric definition lives inside the BI product and is the BI tool's own master. This is why BI legitimately masters `semantic_metrics` natively.
- **Standalone headless layer.** dbt Semantic Layer (MetricFlow) and Cube define metrics in a config layer between warehouse and BI tools, exposed by API to many consumers. Sources are explicit that this is a SEPARATE category: "standalone metrics layers like dbt Semantic Layer and Cube ... while BI-native semantic layers like Looker (LookML), Power BI (DAX) embed metric definitions inside the BI tool itself." In our catalog this is METRICS-LAYER (137, "Metrics Layer / Headless BI"), which masters `metric_definitions`, `dimensional_models`, `metric_access_policies`.
- **The integration is real and one-directional.** ThoughtSpot ingests dbt MetricFlow and Snowflake Semantic Views and converts them into native ThoughtSpot Models, eliminating the need to maintain separate models. So BI tools CONSUME the headless layer when present, but still master their own native model. Catalog reality matches: `semantic_metrics` is mastered by BOTH BI (74) and DATA-AI-PLAT (129); METRICS-LAYER masters `metric_definitions` and BI consumes it (handoffs 218/692/695/696).

Conclusion for the q-file: BI masters its own native `semantic_metrics` (do NOT promote it out to METRICS-LAYER), and consumes the headless layer's `metric_definitions` / `dimensional_models` / `metric_access_policies`. The two are different products with different buyers; the standalone layer is already its own domain. No reversal of the current dual-master shape.

## Workflow substrate (lifecycle and transitions)

- **Content lifecycle (draft to published to deprecated/archived)** is universal: Power BI, Tableau, Looker, Qlik, ThoughtSpot all move authored content from a private/draft state to a published state visible to consumers, then to deprecated/archived. Reports and dashboards exhibit this; the publish step is the gate.
- **External sharing as a distinct, privacy-relevant transition** is present in all (publish-to-web / external share toggles), and is the trigger for the BI to DLP handoff (690).
- **Subscription lifecycle (active to paused to failed to canceled)** is exhibited by all (Power BI subscriptions, Tableau subscriptions, Looker schedules, Qlik subscriptions, ThoughtSpot schedules), including a failed-delivery state.
- **Alerts as event-driven, distinct from subscriptions (recurring cadence)** is explicit in every vendor: Tableau separates data-driven alerts from subscriptions; Looker separates alerts from scheduled delivery; Qlik separates alerting from subscription reports. This grounds bi_alerts (B3-3) as a real, separate master, not a subscription variant.
- **Metric certification** is a single-steward sign-off in the governed-metric model (a metric is "certified" by a data steward). This grounds the has_single_approver flag on the metric.

## Marketed product surfaces (grounds the module-split call)

How vendors package the domain into buyable surfaces:

- **Tableau** packages by PERSONA: Creator ($75), Explorer ($42), Viewer ($15). This is the Creator-vs-Viewer (author vs consume) cut, which maps to a 2-module Content-Authoring + Consumption-Delivery shape.
- **Looker / ThoughtSpot** package by LAYER: the modeling surface (LookML model / ThoughtSpot Model) is operated by a different role than the visualization surface (Look/Dashboard, Liveboard/Answer). This maps to a 3-module Semantic-Modeling + Visualization + Distribution shape.
- **Power BI** packages by CAPACITY/EDITION (Pro, Premium-Per-User, Fabric F-SKU) where viewer access becomes free at F64; the authoring vs consumption split persists across editions.
- **Embedded analytics** is a distinct developer-led buying motion: Power BI Embedded, Sisense (developer-focused SDK/APIs), Tableau Next External Embedding SDK (2025). Sources: "neither [Tableau nor Power BI] is architecturally optimized for the embedded use case ... the embedded analytics market is increasingly distinct from traditional dashboard-centric BI." This is why bi_embed_artifacts (B3-5) could justify its own module and grow a 3-module cut to 4.

## Modularization hypothesis

The vendor evidence supports two equally defensible cuts, with a fourth-module option:

- **2-module (Tableau/Power BI persona shape):** Content-Authoring (data sources + native semantic metrics + queries + dashboards + reports + workspaces + calculated fields + RLS) and Consumption-Delivery (subscriptions + alerts + the published/shared lifecycle). Maps to the Creator-vs-Viewer license split.
- **3-module (Looker/ThoughtSpot layer shape):** Semantic-Modeling (data sources + native semantic metrics + queries + workspaces + RLS), Visualization (dashboards + reports + calculated fields), Distribution (subscriptions + alerts + delivery). Maps to the modeling-vs-visualization role split.
- **Optional 4th module, Embedded-Analytics:** justified by the distinct developer-led buying motion; only if B3-5 (bi_embed_artifacts) lands as confirmed. Grows the 3-module cut to 4.

Either cut clears the Rule #14 floor (BI has well above 3 capabilities). The choice is editorial; both are vendor-grounded.
