# DI Phase 0 — Vendor Surface (2026-06-08)

Market confirmed from live catalog (domain_id=89): **Data Integration** = bulk and streaming
data movement, ELT/ETL, replication, and change-data-capture for analytical workloads and
warehouses/lakehouses. The domain row's own description draws the boundary explicitly:
"Distinct from iPaaS (transactional app integration)." This Phase 0 grounds "what DI masters
vs consumes" in that boundary: DI masters the data-pipeline runtime substrate (connectors,
runs, transformation jobs, schemas, CDC streams, orchestration flows) and CONSUMES the
warehouse/lakehouse tables and the platform-level data_pipelines mastered by DATA-AI-PLAT.
App-to-app integration flows are IPAAS; data-quality rules are DQ; the catalog/lineage register
is DCG.

Key reads:
- **The ingest surface (source_connectors + pipeline_runs + CDC + connector_tasks + credentials)**
  is universal: every flagship masters it. Fivetran/Airbyte are the cleanest; Confluent/Qlik/Striim
  add the streaming/replication runtime; Informatica CDIR packages it as a named module.
- **The transform/deliver surface (transformation_jobs + sink_connectors + schema_registries +
  integration_flows + lineage)** is the second pillar: dbt/Matillion/Informatica CDI are the leaders;
  Confluent contributes governed schema; Qlik/Striim contribute lineage on the replication side.
- **schema_registries is split-spanning.** Confluent and Informatica enforce schema at INGEST
  (drift detection), while dbt enforces it at TRANSFORM (model contracts). The catalog already
  masters one `schema_registries` entity; it belongs on the transform/deliver side as the governed
  schema-of-record, with the ingest side detecting drift against it. This is a "governs both, mastered
  once" pattern, not a reason to duplicate.

## Compliance entities (non-optional for regulated CDC)

The DI market itself is not a regulated-product market the way ATS (FCRA) or healthcare (HIPAA)
is: DI is the data CARRIER, not the data owner. But the regulated-CDC specialists (Qlik Replicate,
Striim) compete specifically on the audit-trail and lineage surface that regulators require when
sensitive data moves. The compliance shape DI exposes is an audit/lineage substrate, not a set of
statute-prefixed master entities:

| Entity | Regulation surface | Proposed module |
| --- | --- | --- |
| data_lineage_events | SOX ITGC (change management evidence), GDPR Art. 30 records of processing | DI-TRANSFORM-DELIVER |
| pipeline_runs audit fields (who/when/what moved) | SOX, HIPAA 164.312(b) audit controls | DI-INGEST-CDC |

No `fcra_*` / `hipaa_*` / `gdpr_*` master entities belong in DI: the data subject is identified
elsewhere (CRM, HCM, EHR, claims, GL). DI's regulatory role is INDIRECT — it is the cross-border /
ePHI / financial-data transfer surface. Whether to tag GDPR/HIPAA/SOX onto the domain at all is a
catalog-policy call surfaced to the user (q7); the vendor evidence supports indirect applicability,
not in-scope mastery.

## Modularization hypothesis

The flagship product packaging draws the split cleanly along ingest-vs-deliver:

1. **DI-INGEST-CDC** — the ingestion + replication runtime. Masters `source_connectors`,
   `change_data_capture_streams`, `pipeline_runs`, and (if loaded) `connector_tasks`,
   `connection_credentials`, `stream_topics`. This is Fivetran / Airbyte / Confluent Connect /
   Qlik Replicate / Striim territory, and the named module in Informatica IDMC ("Cloud Data
   Ingestion and Replication", CDIR).

2. **DI-TRANSFORM-DELIVER** — the in-warehouse transformation + sink + governed-schema +
   orchestration surface. Masters `transformation_jobs`, `sink_connectors`, `schema_registries`,
   `integration_flows`, and (if loaded) `data_lineage_events`, `data_contracts`,
   `transformation_models`, `deployment_environments`. This is dbt / Matillion / Informatica CDI
   territory ("Cloud Data Integration", the transformation+orchestration module).

Why this split over the alternatives:
- **Per-runtime split (batch / streaming / CDC / transform, 4 modules):** maps to vendor product
  navigation more literally, but the four runtimes share the same master set (a `pipeline_run` is a
  `pipeline_run` whether batch or streaming), so the split duplicates masters across modules and
  doubles authoring cost without a distinct entity surface per module. Defensible only if streaming
  is later promoted to its own STREAMING-PLATFORM domain (topics + partitions + consumer groups),
  which is a genuinely different surface (Confluent/MSK/Redpanda).
- **Per-vendor-cluster split (3 modules):** vendor-coupled, violates Rule #18's spirit (modules
  shouldn't trace a vendor's product line), and the clusters overlap (Informatica spans all three).
- **The 2-module ingest/deliver split is the most vendor-neutral cut that still matches how the
  packaging suites (Informatica CDIR vs CDI, Matillion orchestration vs transformation pipelines)
  actually divide the surface,** and it absorbs the Bucket-3 additive entities (connector_tasks,
  lineage events, contracts, models, environments) without re-splitting.

Promotion candidates (not DI modules): a dedicated **STREAMING-PLATFORM** domain (managed Kafka:
topics, partitions, consumer groups as the deployable surface — Confluent Cloud, MSK, Redpanda) and
a **DATA-OBSERVABILITY** domain (Monte Carlo, Bigeye — aggregates DI's freshness/lag/volume signals
rather than running pipelines). Both are distinct markets, not DI modules; they remain queued
candidates, not blockers.
