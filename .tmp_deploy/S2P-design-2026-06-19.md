## 3. The AP-AUTO / invoice-payment boundary (the key finding)

The catalog ALREADY resolves this boundary cleanly; it is NOT genuinely ambiguous:

- **supplier_invoices (75): S2P is the ONLY `master` anywhere.** AP-AUTO holds it at role=`contributor`,
  not master. So the supplier-invoice RECORD (capture, ingestion, e-invoicing compliance) is S2P's.
- **invoice_matches (204): mastered by AP-AUTO.** The three-way-match result object is AP-AUTO's.
- **payment_runs (205): mastered by AP-AUTO.** The disbursement object is AP-AUTO's.
- Live handoff 545 (`invoice_match.exception_raised`, AP-AUTO -> S2P) and 581/583/584
  (S2P -> AP-AUTO on PO/GR events) confirm the wiring: matching and pay sit downstream in AP-AUTO,
  S2P feeds it the PO/GR/invoice records.

Therefore the seam is: **S2P-INVOICE-CAPTURE masters supplier_invoices (the record + e-invoicing
compliance cluster); AP-AUTO retains invoice_matches + payment_runs.** S2P hands off at
`supplier_invoice.captured` / `.approved`. This MATCHES vendor reality (Phase 0): Ariba stops at a
payment_request handed to ERP; Basware's whole business is capture->match->pay but the catalog has
chosen to split match+pay into AP-AUTO. The prior q-file offered "S2P owns invoice matching" as an
option; the live `invoice_matches` master in AP-AUTO makes that the dispreferred choice (it would
require re-mastering an object AP-AUTO already owns). The q-file recommends the consume option and
names the alternative honestly.

## 4. Module split (gated decision q1) - Phase-0-grounded

Phase 0 verdict: vendor evidence cleanly supports FOUR strong standalone modules and one soft seam.

| Module | Master(s) | Phase-0 verdict | Vendors who sell it as a discrete module |
|---|---|---|---|
| S2P-SOURCING | sourcing_events | STRONG standalone | Coupa (Sourcing+CSO), Ariba (Strategic Sourcing Suite), Ivalua, GEP, JAGGAER, Zip |
| S2P-REQ-TO-PO | purchase_requisitions + purchase_orders | STRONG standalone | every suite vendor (Coupa Procurement, Ariba Buying, Ivalua eProcurement, GEP P2P, JAGGAER eProcurement) |
| S2P-RECEIVING | goods_receipts | WEAK standalone (FOLD candidate) | NO vendor sells receiving as a separate module; it sits inside Procurement/P2P everywhere |
| S2P-INVOICE-CAPTURE | supplier_invoices | STRONG standalone | Ariba (Buying and Invoicing), Ivalua, Coupa, JAGGAER (Invoicing), Basware (whole business) |
| S2P-CATALOG-MGMT | procurement_catalogs + catalog_items (b3) | MEDIUM (soft seam) | Ariba sells Catalog as a separate SKU; Coupa/Ivalua/GEP/JAGGAER fold it into procurement |
| S2P-SPEND-ANALYTICS | spend_categories (optional) | optional | every suite ships a separate Spend Analysis module |

**RFP/RFQ home: S2P-SOURCING** (canonical across all six suite vendors; RFx is NOT in Procurement).

### The honest split options for q1
- **Option A (4 modules, vendor-majority):** Sourcing / Req-to-PO (absorbs goods_receipts + intake) /
  Invoice-Capture / Catalog. This is the cleanest read of the vendor surface: no vendor sells
  receiving standalone, so goods_receipts folds into Req-to-PO. Catalog stays separate (Ariba
  precedent + distinct objects). Catalog masters (procurement_catalogs/catalog_items) are b3:
  research-then-load, so until those land Catalog is approved-but-empty-pending, or fold Catalog too
  for a 3-module launch.
- **Option B (5 modules):** the four above PLUS a standalone S2P-RECEIVING mastering goods_receipts,
  for receiving-as-capability granularity. Defensible on the existing goods_receipts master, but no
  vendor packages receiving as a sellable module.
- **Option C (3 modules, lean launch):** Sourcing / Req-to-PO (absorbs receiving + catalog) /
  Invoice-Capture. Defer Catalog and Receiving as separate modules. Lightest build.

Naming change from prior state: the invoice module is **S2P-INVOICE-CAPTURE** (not the old
`S2P-INVOICE-MATCHING`), because matching is AP-AUTO's, not S2P's.
