# VSDP Phase 0 vendor-surface report (Value Stream Delivery Platform / Software Delivery)

Date: 2026-06-13. Scope: READ-ONLY research artifact. No DB or Semantius writes were made.

Domain: VSDP (domain_id 80), UNBUILT (0 domain_modules). Currently masters 8 entities:
`source_repositories`, `code_commits`, `pull_requests`, `ci_pipelines`, `ci_pipeline_runs`,
`build_artifacts`, `software_deployments`, `value_stream_metrics`. The VSDP market is the
software-delivery / value-stream-delivery platform space: source control plus code review,
CI/CD pipeline orchestration, build and artifact management, deployment and release
orchestration, and value-stream analytics (DORA and flow metrics). This report is the
upstream evidence for `audits/VSDP/q-VSDP.md`; q-file recommendations cite the named-vendor
findings below inline.

---

## 1. Flagship vendors

The market splits into three archetypes: broad consolidated platforms, CI/CD and delivery
pure-plays, and value-stream-management (VSM) analytics pure-plays. The supply-chain-security
angle threads through several but is owned by none of them.

- **GitLab Ultimate** (broad platform). The canonical "single application for the entire DevSecOps
  lifecycle" pitch: SCM, MRs, CI/CD, registry, security scanning, and value-stream analytics in one
  product. Packaged as **tiers** (Free / Premium / Ultimate), not as separately-priced stages. The
  whole pipeline is one product; you buy a higher tier to unlock more of it (compliance, security
  dashboards, value-stream analytics live in Premium/Ultimate).

- **GitHub Enterprise** (broad platform, modular SKUs). SCM plus pull requests plus **GitHub Actions**
  (CI/CD) plus **GitHub Advanced Security** (GHAS: code/secret/dependency scanning, now also sold as
  GitHub Secure / standalone Secret Protection and Code Security SKUs). Actions is metered separately
  (compute minutes), and GHAS is a distinct add-on per active committer. So GitHub *does* split
  source-control vs CI vs security into distinct commercial surfaces, unlike GitLab tiers.

- **Azure DevOps Services** (broad platform, named sub-services). Explicitly factored into five
  services: **Repos, Pipelines, Artifacts, Test Plans, Boards**. Each is individually addressable and
  Artifacts/Test Plans/Pipelines parallelism are separately metered. This is the clearest real-world
  evidence that the market *can* be sliced into source-control / CI-CD / artifacts / test / work-items.

- **Atlassian (Bitbucket + Bitbucket Pipelines + Bamboo)**. Bitbucket = SCM and PRs; **Bitbucket
  Pipelines** = cloud CI/CD bolted onto the repo; **Bamboo** = the legacy server-side CI/CD/deployment
  product (on the Data Center track). Atlassian sells SCM and CI together (Pipelines is a feature of
  Bitbucket) but keeps Bamboo as a separate deployment-capable product.

- **Jenkins / CloudBees** (CI/CD pure-play, broad delivery on the commercial side). Jenkins is the OSS
  CI automation server; **CloudBees CI** is the supported enterprise distribution, and CloudBees has
  expanded into feature-flag management (acquired Rollout) and a broader software-delivery platform with
  VSM/flow reporting. CI/CD is the core; deployment and analytics are add-on surfaces.

- **CircleCI** (CI/CD pure-play). Hosted/self-hosted CI/CD only: pipelines, runs, orchestration, artifact
  caching. No SCM, no deployment-target ownership beyond pipeline steps. Sells the CI/CD slice on usage
  (credits/compute), nothing else.

- **Harness CD** (deployment/delivery pure-play, now a modular platform). Modern continuous-delivery
  engine built around deployment strategies (canary, blue-green), feature flags, and a separate Harness
  CI module. Harness packages as **distinct priced modules** (CI, CD, Feature Flags, Cloud Cost, Security
  Testing Orchestration), the strongest pure-play case for per-stage modularity.

- **Argo CD** (deployment pure-play, GitOps). CNCF OSS continuous-delivery to Kubernetes; declarative
  GitOps reconciliation of desired state. Owns the *deployment* slice for K8s only; no SCM, no general
  CI, no analytics. Often paired with Argo Workflows/Rollouts.

- **Octopus Deploy** (deployment/release-orchestration pure-play). Release and deployment orchestration
  across environments (the `deployment_environments` plus `deployment_strategies` surface) decoupled from
  whatever CI built the artifact. Owns deployment and release versioning; defers CI to others.

- **Plandek** (VSM analytics pure-play). Engineering-intelligence and value-stream metrics layered *over*
  Jira/Git/CI tools. Sells **only the analytics slice** (flow, DORA, delivery predictability). It masters
  no repos, pipelines, or deployments; it ingests and normalizes them into metrics.

- **LinearB** (VSM / engineering-metrics pure-play). Same archetype as Plandek: DORA and developer-workflow
  metrics, PR-cycle-time analytics, "WorkerB" automation over the existing pipeline. Sells only the
  measurement and workflow-optimization slice.

Supply-chain-security angle: GitHub Advanced Security and GitLab Ultimate surface dependency/SAST/secret
findings and (GitHub) artifact attestations and SBOM export, but neither *is* a supply-chain-security
product. Dedicated owners (Snyk, Chainguard, Sigstore/cosign, JFrog Xray) sit in AppSec / supply-chain
domains, not VSDP.

## 3. Module-shape evidence (drives the q-file)

### How the flagships package the market

- **GitLab** packages it as **one consolidated product**, gated by tier, not by stage. Buying Ultimate
  gives you SCM + CI/CD + registry + security + value-stream analytics as a single application. This is
  the explicit "one tool, one model" position and the strongest evidence for option (a).
- **GitHub** packages **distinct SKUs**: the platform (Enterprise seats), **Actions** (metered CI compute),
  and **Advanced Security** (per-committer add-on). Source control, CI, and security are commercially
  separable. This is evidence *against* one undifferentiated blob, but the seams it cuts are
  SCM | CI | security, not the four-way dev/CI/deploy/analytics split.
- **Azure DevOps** is the cleanest modular case: five named services (**Repos / Pipelines / Artifacts /
  Test Plans / Boards**), each separately addressable and partly separately metered. This is the strongest
  real-world support for a multi-module VSDP, and notably it carves **artifacts** and **test** out as
  first-class peers of repos and pipelines.
- **Atlassian** bundles SCM+CI (Pipelines is part of Bitbucket) but keeps **Bamboo** as a separate
  deployment-capable product, an implicit SCM/CI vs deployment seam.
- **Harness** sells **per-stage priced modules** (CI, CD, Feature Flags, etc.), the strongest pure-play
  evidence that CI and CD are separable products with independent buyers.
- **Plandek and LinearB** sell **only the analytics slice** and master none of the upstream entities,
  proving value-stream analytics is a commercially viable standalone surface (a real seam, not just a
  feature).

### The four options, evaluated

- **(a) One consolidated VSDP-PLATFORM module.** Matches GitLab Ultimate's positioning exactly and is how
  the single largest "everything" vendor sells. Weakness: it ignores that GitHub, Azure DevOps, Harness,
  and the entire VSM pure-play tier all monetize sub-slices separately, and it collides with domain-map
  Rule #14 (a domain with three-plus capabilities wants at least two modules). Defensible only if VSDP
  must stay minimal.

- **(b) 2-split: VSDP-DEV-PIPELINE (source-control + CI/CD + artifacts) + VSDP-DELIVERY-AND-VSM
  (deployment + value-stream analytics).** Supported by the convergent seam every modular vendor draws:
  Atlassian (Bitbucket/Pipelines vs Bamboo), Harness (CI vs CD), and the Plandek/LinearB tier (everything
  upstream vs the measurement-and-delivery view). It clears the Rule #14 floor with the minimal shape and
  groups artifacts with the pipeline that produces them (matching GitLab/GitHub/Azure, where the registry
  sits next to CI). The deployment-plus-analytics module mirrors the Octopus + Plandek/LinearB "what
  shipped and how well it flows" surface.

- **(c) 4-split: SOURCE-CONTROL + CICD + DEPLOYMENT-MGMT + VALUE-STREAM-ANALYTICS.** This is exactly the
  Azure DevOps factoring (minus Test/Boards) and how Harness + Argo/Octopus + Plandek would look if each
  pure-play were a module. It is the most "vendor-true" to the modular sellers, but it over-fragments
  *before* the per-module persona/RACI/lifecycle substrate exists: source-control and CI/CD share repos,
  commits, runs, and runners so tightly that splitting them creates cross-module FK churn with no buyer
  who actually purchases source-control alone (nobody sells bare SCM as a standalone enterprise module;
  even GitHub bundles repos with the platform seat).

- **(d) Monolith + VSDP-STARTER for SMB.** A packaging trick (the GitLab-Free-vs-Ultimate or
  Bitbucket-Cloud-vs-DC pattern), not a domain decomposition. It answers "which tier" not "which sub-area"
  and does not give the catalog distinct capability groupings to hang work on.

### Verdict

The vendor packaging most supports **(b), the 2-split**, as the build shape, with **(c)** as the
evolution target once the substrate matures. Reasoning by vendor: the only seam that *every* modular
seller agrees on is upstream-build vs downstream-deliver-and-measure: Atlassian (Pipelines vs Bamboo),
Harness (CI vs CD), Octopus (deploy-only), and Plandek/LinearB (measure-only) all cut there. GitLab's
consolidated tier argues against fragmenting *more* than necessary, which rules out (c) at build time.
Azure DevOps proves a finer split is *possible* later but bundles artifacts with the build side, which is
why artifacts belong in VSDP-DEV-PIPELINE under (b), not in a deployment module. (b) is the minimal split
that is simultaneously Rule-14-compliant and faithful to the one seam all vendors share.

## 4. Per-decision verdicts

### test_runs mastery

GitLab and Azure DevOps do **not** blur CI pipeline runs and test runs into one record. In Azure DevOps,
**Test Plans** is a separate named service from **Pipelines**, and test results are first-class objects
(test runs, test results, flaky-test analytics) distinct from the pipeline run that triggered them; a
pipeline run *references* test runs via the publish-test-results task. GitLab similarly keeps the CI job
(`ci_pipeline_runs` analog) distinct from test reports it ingests (JUnit artifacts surfaced as test
reports), and the test-case detail lives in its own surface. CircleCI/Jenkins likewise treat test results
as artifacts/reports attached to a run, not as the run itself.
**Verdict:** `test_runs` should stay canonically mastered by a **Test Management** domain, not be embedded
in a VSDP CI/CD module. The vendor boundary holds: CI/CD *orchestrates and triggers* test execution and
*references* the results, while assertion authoring, test-case lifecycle, and result detail are a separate
mastery (Azure's Test-Plans-vs-Pipelines split is the cleanest proof). A VSDP CI/CD module links to
test_runs; it does not own them. (Supports q-VSDP q3 = a.)

### software_deployments role

Octopus, Argo CD, and Harness treat a deployment as a **real master event**: a discrete release of a
specific artifact/version to a specific environment with a lifecycle (queued, in-progress, succeeded,
rolled-back). Argo reconciles desired state into an actual sync/deployment record; Octopus records each
deployment of a release to an environment. By contrast, **Plandek and LinearB** never master deployments,
they *derive* deployment-frequency and change-failure-rate metrics by normalizing signals pulled from the
underlying CI/CD and incident tools (the VSM normalization model: deployment is a computed event, not an
owned one).
**Verdict:** keep `software_deployments` as the **umbrella master event** that platform-specific
realizations (Helm releases, PaaS deployments, Argo syncs) instantiate, not a derived rollup. Rationale by
vendor: the deployment-owning tools (Octopus/Argo/Harness) all persist it as a first-class record, and a
single canonical release event is what cross-domain handoffs (incident, change, observability) attach to.
The Plandek/LinearB derived shape only pays off once a normalization layer over multiple platform masters
actually exists, which VSDP does not yet have. (Supports q-VSDP q4 = a.)

### solutions inventory (primary vs secondary)

- **Primary coverage** (broad platforms that span most of the matrix, anchor the union surface):
  **GitLab Ultimate, GitHub Enterprise (with Actions + Advanced Security rolled up), Azure DevOps
  Services.** These three define the consolidated-platform shape and cover repos through analytics.
- **Secondary coverage** (CI/CD and delivery specialists that validate sub-slices): **Jenkins/CloudBees,
  CircleCI, Buildkite, Harness CD, Argo CD, Octopus Deploy**, plus the **Atlassian** delivery surface
  (Bitbucket + Bitbucket Pipelines + Bamboo).
- **VSM pure-play coverage** (keep the value-stream-analytics surface honest): **Plandek, LinearB.**
**Verdict:** author the full set, primary plus secondary plus the two VSM pure-plays, in one load. The VSM
pure-plays are non-optional because without them `value_stream_metrics` looks like a GitLab/Azure feature
rather than a market with standalone vendors. Adding Atlassian in the same pass keeps the inventory
complete and avoids a second loader run. (Supports q-VSDP q2 = c and q5 = a.)

### regulations / compliance frameworks

The VSDP market **surfaces** supply-chain-security signals but does not **carry** the frameworks as its
own subject. What the platforms actually surface: **GitHub Advanced Security** provides SAST (CodeQL),
secret scanning, dependency review, **artifact attestations**, and SBOM export, evidence that *maps to*
SLSA build-provenance levels and NIST SSDF practices but is sold as a security add-on, not as a compliance
module. **GitLab Ultimate** surfaces security dashboards, dependency/container scanning, and compliance
frameworks/pipelines (the compliance-pipeline feature), again as a tier capability over the pipeline.
Neither platform models NIST SSDF (SP 800-218), EO 14028, the EU Cyber Resilience Act, or SLSA as
governed framework objects; those are the subject matter of dedicated **AppSec** and **supply-chain
security** domains (where Snyk, Chainguard, Sigstore, JFrog Xray live).
**Verdict:** attach **no** compliance frameworks to VSDP itself, keep supply-chain regulation on the
candidate AppSec / supply-chain-security domains, the way employment law attaches to the hiring domain and
not to the delivery pipeline that happens to enforce a gate. VSDP *consumes and enforces* policy (build
gates, attestation requirements) but is not the regulation's home. Pick the partial-attach alternative
(SLSA + NIST SSDF on VSDP) only if build-artifact lifecycle policy must be enforceable directly from this
domain. (Supports q-VSDP q6 = a.)

### candidate entities (15) quick disposition

Native-additive once modules exist (near-universal Common): `deployment_environments`, `secrets`,
`container_images`, `runners`, `release_versions`, `deployment_strategies`. SCM-edge, GitHub-anchored:
`branch_protection_rules`, `merge_queues` (real but narrow, mostly GitHub). Consume-from-another-domain
(Specialist/add-on, owned elsewhere): `feature_flags` (feature-flag-management domain / LaunchDarkly,
Harness FF), `sboms`, `supply_chain_attestations`, `vulnerability_findings` (AppSec / supply-chain
security), `package_registries` (artifact-registry, e.g. JFrog, overlaps `build_artifacts`), `iac_modules`
(IaC/platform-engineering), `engineering_workflows` (overlaps VSM analytics + work-tracking). All additive,
all after the build, several pending whether the candidate-queue domains get promoted. (Supports
q-VSDP q9 = yes, additive, post-build.)
