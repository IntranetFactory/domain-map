# SCA Phase 0 — Vendor Surface

Software Composition Analysis: open-source dependency inventory, license identification & obligation/policy enforcement (GPL/copyleft), OSS vulnerability detection, SBOM generation & management, supply-chain risk. Backs the IP Legal agent (OSS Compliance Checker).

## Catalog check (live reads)

- No SCA vendors present. `solutions` ilike snyk/sonatype/fossa/black duck/mend/whitesource/endor returned only Mendix (low-code) and ProcessUnity (TPRM). No overlap.
- No SCA data objects present. No `dependency_components`, `sbom_documents`, `license_findings`, `license_policies`, `policy_violations`.
- Adjacent security domains exist: **VULN-MGMT** (Vulnerability Management), SECOPS, DSPM, SOAR. VULN-MGMT masters `vulnerabilities`, `vulnerability_definitions`, `vulnerability_scans`, `vulnerability_remediations`, `vulnerability_exceptions`, `vulnerability_assessments` — infra/endpoint/app CVEs against assets from ITAM/CMDB. It does **not** model dependencies, licenses, or SBOMs.
- Adjacent legal/compliance: **GRC**, **LEGAL-PRACT-MGMT**, **LSD**. None model OSS license obligations.

Verdict: genuine gap. SCA attaches to neither cluster cleanly; see modularization below.

## Modularization hypothesis

Six candidate modules, each with a master (Rule #14 satisfied):

1. **INVENTORY** — the shared substrate: `projects`, `repositories`, `scans`, `dependency_components`, `component_versions`, `dependency_edges`, `integrations`, `knowledge_base_entries`. The dependency graph both faces read from.
2. **LICENSE-COMPLIANCE** (legal face) — `license_findings`, `licenses`, `license_obligations`, `attribution_reports`. IP/legal obligation surface.
3. **SUPPLY-CHAIN-RISK** (security face) — `vulnerability_findings`, `vulnerability_advisories`, `reachability_analyses`, `malicious_package_alerts`. OSS app-sec surface.
4. **GOVERNANCE** — `policies`, `policy_violations`, `policy_evaluations`, `waivers`, `finding_status_transitions`, `notifications`, `audit_logs`. Cross-face policy engine (license AND vuln policies unify here).
5. **REMEDIATION** — `remediation_tasks`, `remediation_pull_requests`, `upgrade_suggestions`. Shared fix workflow (a version bump fixes both a CVE and a license issue).
6. **SBOM-MGMT** — `sbom_documents`, `sbom_components`, `vex_statements`, `ai_bom_records`, `cra_conformity_records`. Regulatory artifact production consumed by both faces.

## Module hypothesis: ONE domain, two faces

**SCA is one domain with two functional faces, not two domains.** The license face and the vulnerability face share the same physical substrate (INVENTORY: one dependency graph feeds both), the same policy engine (GOVERNANCE: license-policy and vuln-policy are the same `policies`/`policy_violations` shape), the same fix workflow (REMEDIATION: one version bump resolves both), and the same regulatory artifact (SBOM-MGMT: one SBOM carries both component licenses and known vulns/VEX). Splitting would fork these four shared modules and duplicate the graph. The legal/security distinction is real but lives at the module tier (LICENSE-COMPLIANCE vs SUPPLY-CHAIN-RISK), not the domain tier. Every SCA flagship ships both faces from one scan — that co-location is the domain boundary.

## License-vs-security clustering read

SCA does not belong wholly in either the legal cluster or the security cluster; it is a **bridge domain**. Its center of gravity leans **security** (it lives in the SDLC/CI, scans code, and every vendor is an app-sec tool first). But its distinguishing, non-duplicable value versus VULN-MGMT is the **legal** face: license identification and copyleft/attribution obligation enforcement, which no security domain models.

Recommended placement: seat SCA in the **security cluster adjacent to VULN-MGMT**, with an explicit cross-cluster edge to the legal cluster (GRC / LSD) via the LICENSE-COMPLIANCE module, since it backs the IP Legal agent. Boundary with VULN-MGMT: VULN-MGMT owns CVEs on deployed **assets** (ITAM/CMDB-linked, infra + running apps); SCA owns findings on **source dependencies** pre-deploy (components + licenses + SBOM). `vulnerability_findings` here is scoped to OSS components (hence the distinct name from VULN-MGMT's `vulnerabilities`) to avoid collision. They hand off, they do not merge.
